How a p5.js sketch becomes a plot

p5 helpers and an object that draws supported shapes while recording their coordinates for the pen. This handbook explains what each method does, what it maps to in the engine, what it deliberately does not do, and where a sketch can go wrong.

1The adapter

The adapter draws supported p5 shapes and records their coordinates for the pen. Geometry, planning and machine control come from vanilla.penplotter. Its main p5 helpers are:

methodwhat it is for
createPlot(options)the one you will use: an object whose shape methods draw on the canvas and record the same shape in millimetres; go() sends it to the pen.
createPlotterEngine(options)the bare engine with the canvas size as its page, when you want to talk to it directly.
drawRoute(plan, options)draws a plan the way the machine will draw it: the real order, reversed paths, moved seams.

Everything else, geometry, optimisation, route planning, exports, machine profiles and the driver, lives in vanilla.penplotter, which knows nothing about p5. The adapter contains no copy of any of it; a bug in the pipeline is fixed there, once, for both libraries. The one piece of real work the adapter does own is the translation from canvas pixels to millimetres on the bed.

It is not p5.plotSvg, which records a sketch between beginRecordSvg() and endRecordSvg() into an SVG file and covers far more of p5's drawing API. That library stops at the file on purpose; this adapter can plot directly and also export through its engine. Supported SVG paths and basic shapes can be imported in the core's SVG to pen example; arbitrary SVG features are not reproduced.

2Installing: the version contract

This handbook covers current source. The latest tags are core v0.3.1 and adapter v0.2.1. Newer pen(), drawRoute() and bed helpers are not all in those tags; use the earlier tool(), drawPreview() or drawPlotPlan() names with a tagged build.

The connection is explicit. The adapter is handed the p5 constructor and the engine class, and, when you want to plot, the engine's driver module:

import { PlotterEngine } from "https://cdn.jsdelivr.net/gh/seb-prjcts-be/vanilla.penplotter@v0.3.1/vanilla.penplotter.js";
import * as Ebb from "https://cdn.jsdelivr.net/gh/seb-prjcts-be/vanilla.penplotter@v0.3.1/src/driver/ebb.js";
import { installP5Penplotter } from "https://cdn.jsdelivr.net/gh/seb-prjcts-be/p5.penplotter@v0.2.1/p5.penplotter.js";

installP5Penplotter(p5, PlotterEngine, { driver: Ebb });

Why not auto-detect a global? Because load order and versions would become invisible, and the first thing that goes wrong with two libraries loaded from two places is a version mismatch nobody can see. So the contract is written down once, in code, as REQUIRES = { core: "0.2.0", p5: "2.2.2" }, and everything else is tested against it: package.json's peer dependencies, the manifest, and the Requirements table in the README, which is byte for byte the same table as in the engine's README.

When connecting, the adapter checks three things. p5 must be a constructor with a prototype. PlotterEngine must be a class. And when a driver is passed, it must expose EbbDriver, createWebSerialTransport and EBB_PROFILES, and the engine's static version must be 0.2.0 or newer, because an older engine has no driver at all. The refusal is a plain sentence: "p5.penplotter needs vanilla.penplotter 0.2.0 or newer for direct plotting; this one is 0.1.9. Update vanilla.penplotter first." Without a driver, nothing is checked and createPlotterEngine() and drawRoute() work with any engine; only go() will throw.

Pinned or latestThe jsDelivr URLs above are pinned to a tag: the library versions stay fixed. Test the pinned pair with your sketch. The GitHub Pages URLs (https://seb-prjcts-be.github.io/…/) always serve the latest main of both libraries, which is what the site's own examples use, with the version check as their guardrail. After an update, a browser can hold the old engine in its cache and the adapter will refuse it, correctly; reload with Ctrl+F5.

3Wiring a sketch: four ways and one timeline

Both libraries are ES modules, and a module has two properties that decide every setup: it creates no globals, so a function setup() written inside a module is invisible to p5's global mode, and it is deferred, so it runs after the page has been read but before the load event on which p5 starts a global-mode sketch. The timeline of any page is therefore:

1. p5.js loads                          (classic script, runs at once)
2. classic scripts run in order         (your sketch.js defines setup/draw)
3. page fully read
4. module scripts run                   (the adapter is installed here)
5. DOMContentLoaded
6. load  →  p5 calls window.setup()     (createPlot already exists)

The four ways to place the three import lines on that timeline, in order of simplicity:

  1. Global mode, wiring in index.html. The imports live in one inline module in index.html; sketch.js is a plain script with no imports, exactly like every other p5 sketch. The one for classrooms and for the p5.js Web Editor. Rules: load p5 before the module; never give sketch.js type="module"; call createPlot() inside setup(), never at the top of the file, because at that moment the adapter is not installed yet.
  2. Instance mode, sketch as a module. The imports move into sketch.js, which hands itself to p5 with new p5(...) and prefixes every p5 call with p.. Self-contained and free of load-order assumptions; the form the library's own examples use for anything that imports.
  3. Global mode from a module. The sketch is a module and publishes its functions itself: window.setup = setup; and so on, one line per p5 callback you use. A callback that is not assigned to window will not be called by p5.
  4. Import maps and local neighbours. Not a fifth form but a refinement of any of the above: bare names like "p5.penplotter" resolved by an import map in index.html, or relative paths to sibling folders while working on the libraries themselves.

The Setup page shows all four in full, with what breaks and how the error reads. Whichever you pick, plotting for real needs the same three things: the driver handed in at install, Chrome or Edge on localhost or https (Web Serial exists nowhere else; not in Firefox, not in Safari, not from a file:// URL; the p5.js Web Editor does work, plotted from it on 2026-10-01), and one click on the drawing, because a browser shows its port list only after a click; plot.go() itself is written at the end of the drawing and waits for that click.

4createPlot(): one object for screen and paper

createPlot(options) returns a P5Plot. Start with a paper format and margin. The canvas is fitted and centred on the sheet; use width when the drawing needs a fixed size in millimetres.

plot = createPlot({ paper: "A2", margin: 12, width: 300 });
// a 300 mm wide drawing, centred on A2 paper
// the scale is 300 / width (of the canvas) mm per pixel
optionmeaningdefault
paper, marginchoose an A0–A6 sheet and its drawing marginno sheet unless selected; margin 12 mm

Inside, the object holds a fresh PlotterEngine in millimetres. Its page is the profile's travel (594 × 432 mm) when a driver was installed, so the engine's bounds check is the machine's; without a driver it is just large enough to hold the canvas at its offset. Two small helpers do all the geometry: toMm(x, y) is offset + pixel · scale, and toPx(point) is its inverse, used to draw the engine's fills back onto the canvas.

clear() replaces the engine with an empty one. That is how a frame starts: every draw() that wants a fresh job calls plot.clear() first, exactly where it calls background(). plan(options) asks the engine for its plan and returns it; engine is the engine itself, for layers, pens and exports the adapter does not wrap.

Paper, drawing and bed

The canvas size is in pixels; width sets its mapped width in millimetres. A 400 × 250 pixel canvas with createPlot({ paper: "A4", margin: 12, width: 80 }) occupies an 80 × 50 mm area centred on A4 paper. A rectangle at (10, 10) with width 380 and height 230 occupies 76 × 46 mm inside it. The paper can be larger and have its own position.

paperportrait, mmlandscape, mm
A4210 × 297297 × 210
A3297 × 420420 × 297
A2420 × 594594 × 420

The HSE/A2 bed is 594 × 432 mm, with X along the long rail. A2 fits with its 594 mm edge along X; centred paper has its nearest corner at X = 0, Y = 6 mm. A machine's model name does not set the drawing size.

Choose an A format

plot = createPlot({ paper: "A2", margin: 12 });

paper accepts A0–A6 through the core's PlotterEngine.paperSize(). The canvas fits proportionally inside paper margins, default 12 mm, and is centred on the sheet. Paper is centred on the installed machine profile's bed; without a profile it starts at X/Y = 0. Default orientation: "auto" follows the canvas aspect ratio and tries the other orientation if needed to fit the bed. Explicit "portrait" or "landscape" is honoured or refused. A2 on the HSE/A2 is 594 × 420 mm at X = 0, Y = 6 mm. A 400 × 250 canvas with a 12 mm margin maps to 570 × 356.25 mm.

paperX/paperY move the sheet; x/y locate the canvas. width or mmPerPixel overrides fitting. plot.paper reports the resolved sheet, used automatically by plot.drawBed(canvas). Invalid paper placement or a canvas outside the margins is refused; plan() also checks recorded strokes before connecting to the machine. Existing sketches without paper keep their mapping. Both libraries need current source for this option.

Show the actual paper

// After recording the drawing; bedCanvas is a separate HTML canvas.
plot.drawBed(bedCanvas, {
  sheet: { x: 60, y: 100, width: 210, height: 297 }
});

sheet gives the actual paper's X/Y position and width/height in millimetres. Without it, drawBed() uses selected plot.paper or, when no paper was selected, the mapped canvas area. The preview draws the existing planned strokes; it does not move, scale or rotate them. Swap the preview sheet's width and height to preview landscape paper. That changes the outline only. Screen rotate() still does not rotate the recorded geometry.

For quarter-turn placement of a complete job, use the core's paper and bed panel. It turns the drawing with the sheet and checks both against their bounds. These bed helpers require current source in both libraries; use the imports on Setup, rather than assuming the tagged builds include them.

5The shape methods, one by one

Every shape method does two things in one call: it calls the same p5 function with the same arguments, so the canvas shows what you wrote in the sketch's current style, and it records the shape in millimetres in the engine. The arguments are p5's, including its habit of taking a diameter where the engine takes a radius.

callon the canvasin the engine
point(x, y)pointa horizontal line of 0.24 mm: a pen cannot dot, it has to move to leave ink
line(x1, y1, x2, y2)lineline
circle(x, y, d)circlecircle with radius d / 2 · scale (a 96-gon)
ellipse(x, y, w, h)ellipsea circle when w === h; otherwise a 96-point polygon sampled at π/48
arc(x, y, w, h, start, stop, mode)arcpoints every π/48 along the ellipse; OPEN (default) a polyline, CHORD a closed polygon, PIE a closed polygon through the centre; angles converted from degrees when angleMode(DEGREES)
rect(x, y, w, h)rectrect, corner mode
square(x, y, s)rectrect
triangle(…), quad(…)triangle, quadclosed polygons
polyline(points)beginShape … vertex … endShape, inside push/noFill/poppolyline
polygon(points)the same, with endShape(CLOSE)polygon

Points for polyline and polygon may be [x, y] pairs or { x, y } objects; both are common in p5 code. Every shape method returns the plot, so calls can be chained. The choices here follow the engine: it flattens a circle to 96 segments, so an oval gets the same; its stipple already drew a quarter-millimetre dash, so a point does too.

6Fills

p5 fills a shape with colour; a pen cannot. The three fill methods hand a polygon to the engine's fills, in millimetres, and draw the resulting lines back onto the canvas with the sketch's current stroke, so screen and paper show the same hatching:

let square = [[20, 80], [120, 80], [120, 180], [20, 180]];
plot.hatch(square, 3, PI / 4);   // spacing 3 mm on the bed, angle in angleMode()
plot.crossHatch(square, 4);      // second pass at right angles
plot.stipple(square, 150, 3);    // 150 dots, seed 3: same seed, same dots

Spacing is a physical distance in millimetres. The resulting tone depends on the pen, ink and paper. Angles follow angleMode(). Hatch lines are separate strokes, not an automatically connected zigzag; stipple centres are drawn as p5 points while the pen records short dashes.

7Recording frames for a plot

The plot contains the geometry recorded since the last clear(). Clearing at the start of draw() replaces the recording for each frame; without it, shapes accumulate. The plan is taken when the plot starts, before the connection is opened. The adapter records coordinates, not every aspect of the screen image.

function draw() {
  background(255);   // screen only: no plot. in front of it, so it is not recorded
  plot.clear();      // new frame, new job
  plot.rect(10, 10, 380, 230);
  plot.line(30, 125, 370, 125);
  plot.go();         // ready: click the drawing to plot
}

Two habits make this comfortable. Call noLoop() in setup() and redraw() on a key when the sketch is generative, to keep the drawing still while plotting; the Molnár grid does this with R for a new seed. And keep randomSeed() at the top of draw(), so the frame you plotted can be drawn again tomorrow. For an animated sketch, clear the recording each frame and pause on the drawing you want to plot. Screen transforms and styling still need explicit handling.

8plot.go(): connect, confirm, plot, stop

go() is one method because a person at a plotter wants one gesture: you write it at the end of the drawing, and a click on the drawing starts the pen. Called from setup() or draw(), where there is no click yet, it writes the safety checklist to the status line and waits for one click on the canvas; that click is the confirmation, and no dialog follows. Called from a key or mouse handler, it goes straight on and asks once with a dialog. A second go() while one is waiting does not queue a second plot. Inside it does four things in order:

  1. Require the driver. Without one installed it throws: "plot.go() needs the driver: installP5Penplotter(p5, PlotterEngine, { driver: Ebb })." If a plot is already running it returns { status: "busy" } and does nothing.
  2. Plan. plan() on the engine, which optimises and orders the frame's geometry.
  3. Connect. connect() reuses an open transport; otherwise it takes a port the browser already granted (navigator.serial.getPorts()) or opens the browser's port picker with no USB filter, so an EBB clone with unusual ids still shows up; the driver's V handshake then decides. A closed picker becomes a plain message: "No plotter was chosen. If no list appeared at all, open this page in Chrome or Edge itself."
  4. Confirm and run. The confirm function (a dialog by default) asks whether the carriage is parked in the home corner, the paper is in place with no magnet in the way, and hands are clear. A refusal returns { status: "cancelled" } and sends nothing. Otherwise driver.run(plan, { confirmed: true }) streams the plan; the result is returned, and the status line reads "plot complete" or "stopped safely: …" on an error, which is then rethrown so the sketch can show it.

While the pen runs, a click on the drawing calls stop(); so does plot.stop() from your own code. It calls the driver's abort(), which requests the engine's stop sequence: motion cleared, pen up, motors off. A working connection is needed to deliver those commands. Every status change goes through say(): to the log function when you gave one, otherwise to the console. The examples pass a function that writes into a status line on the page.

The confirmation is the adapter's own, on top of the engine's confirmed: true requirement; the bounds check, the speeds, the flow control and the safe stop are the engine's and are not duplicated here. The engine's handbook, chapter 9, describes what happens on the wire.

9createPlotterEngine() and drawRoute()

createPlotterEngine(options) returns a bare PlotterEngine whose page is the current canvas: width and height from the sketch, margin 0, and the unit px unless you say otherwise. It is for sketches that want the engine's full surface, layers, pens, the optimizer's options, the exports, without the draw-and-record object. Because its unit is pixels, such an engine can preview and export (the exports convert pixels to physical sizes at 96 per inch) but cannot plot directly; give it units: "mm" and millimetre coordinates for that, or use createPlot().

drawRoute(plan, options) draws a plan's routes with p5: push, noFill, then for every route a stroke in its tool's colour (or options.stroke), strokeWeight(options.strokeWeight ?? 1), and a beginShape/vertex/endShape; pop at the end. It draws plan.routes, the paths in the order the machine will draw them, never the original artwork, so what you see is the planner's result including reversed paths and moved seams. It refuses anything that is not a vanilla.penplotter/plan@1 with a routes array. drawPlanWithP5(p, plan, options) is the same function without the prototype helper, for code that has a p5 instance in hand.

10What is not recorded

The adapter records the arguments you pass to its shape methods. It does not look at p5's state, and that is the rule to remember when the paper differs from the screen:

  • Transforms. translate(), rotate() and scale() move what the canvas shows, not what is recorded. A shape drawn inside a transform lands on paper untransformed. Compute the transformed coordinates yourself and pass those, or stay in absolute coordinates as the examples do.
  • rectMode and ellipseMode. The canvas honours them; the engine gets corner-mode rectangles and centre-mode ellipses, p5's defaults. Keep the defaults, or convert.
  • Stroke weight and colour. The pen is the pen. Everything is recorded on the engine's default tool; the SVG export has one hairline and the plot has whatever pen is in the holder. For two pens, work on plot.engine directly with tool() and layer().
  • Fills. fill() is a screen thing. Use hatch, crossHatch or stipple.
  • Everything without plot., which is the point: background(), a debug text, a mouse cursor, a grid you draw to help yourself, all stay on screen.

11Sampling waves in a sketch

Math.sin(x) returns a number; the adapter receives the resulting points. Build ordinary points with it and pass them to polyline. Two things matter for paper: pick a fixed t, because the plotter draws one moment, and use the wave for something a pen can show, such as the y of a line, the angle of a field, or the spacing of a hatch.

const points = [];
for (let x = 40; x <= 760; x += 4) {
  points.push({ x, y: 400 + 80 * Math.sin(x * 0.04) });
}
plot.polyline(points);

The Wave field example goes one step further: two waves, one per axis, give every point of the sheet a direction, and sixty lines follow that direction until they leave the frame. The seed picks the wave shape, so different seeds produce different fields.

13Recipes

Rings

function draw() {
  background(255); noFill();
  plot.clear();
  for (let d = 40; d <= 560; d += 20) plot.circle(300, 300, d);
}

A frame you can measure

// 300 px wide canvas, 300 mm on the bed: one pixel is one millimetre, so a 40 px square is 40 mm on paper
plot = createPlot({ paper: "A2", margin: 12, width: 300 });
plot.square(20, 20, 40);

Two pens from a sketch

const engine = plot.engine;                 // the vanilla.penplotter engine behind the plot
engine.tool({ id: "red", color: "#c8402c", width: 0.8 });
engine.layer("accent", { toolId: "red" });   // recorded shapes now land on this layer
plot.circle(300, 300, 200);
engine.layer("default");                     // back to the black pen
plot.rect(20, 20, 560, 560);
// plot.go() pauses once, after the default layer, and asks for the red pen

A series

function draw() {
  randomSeed(seed);
  // … the drawing …
  plot.go();                                           // like it? click it
}

function keyPressed() {
  if (key === "r") { seed += 1; redraw(); }           // look again
}

Plot a transformed shape correctly

// wrong: the rotation is on the canvas only
// rotate(a); plot.rect(0, 0, 100, 40);
// right: rotate the corners yourself and pass a polygon
const corners = [[0, 0], [100, 0], [100, 40], [0, 40]].map(([x, y]) => [
  cx + x * cos(a) - y * sin(a), cy + x * sin(a) + y * cos(a)

15Tests, tooling and the site

npm test runs three Node scripts. tests/snapshot.js connects the adapter to a fake p5 and a fake engine, checks that drawPlanWithP5 makes exactly the expected p5 calls, walks every local link on the site, and checks that every example is in the gallery and the manifest and that the generated architecture page is current. tests/plot.js checks every shape method against the fake engine, the degrees conversion, the scale and offset, go()'s flow with a fake driver kit (connection reuse, cancellation, the missing-driver error), and then, when the engine's checkout is next door, the same against the real engine and its EBB driver: 80 pixels at 200 mm per 400 pixels is 40 mm is 3 200 steps on both motors, hatch lines drawn back equal the paths planned, the same seed gives the same dots, and a canvas placed off the bed is refused. tests/requirements.js checks the version contract everywhere it is stated and compares the shared table with the engine's README.

npm run docs renders the architecture page from Markdown, npm run manifest regenerates the manifest, npm run handbook prints this page to PDF. The GitHub Actions workflow checks out the engine next to the adapter, because both the examples and the tests use it as a sibling folder, and fails when a generated file is stale. Publishing order: the engine first, then the adapter.

16Limits and roadmap

  • No curves: bezier, curve and curveVertex are not wrapped yet. Sample them into points, or draw them with polyline.
  • No transforms, modes, stroke weights or fills, as chapter 10 describes.
  • No layer() or tool() on the plot itself; two pens go through plot.engine.
  • One machine profile, one browser family, one click: the engine's limits are the adapter's.

Arcs are already implemented. General Bézier curves and pen/layer helpers remain possible additions. Mid-stroke pause, resume and live streaming depend on future core work. See the core roadmap for proposed changes.
